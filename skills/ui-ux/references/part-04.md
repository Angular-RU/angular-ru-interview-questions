### Accessibility как часть UX



#### Вопрос: Почему accessibility является частью UX?

**Короткий ответ**

Accessibility делает интерфейс usable для людей с разными возможностями, устройствами и контекстами. Это не отдельная
надстройка, а часть качества пользовательского опыта.

**Полный ответ**

Accessibility влияет на возможность **выполнить пользовательскую задачу**, а не только на формальное соответствие
стандартам. Интерфейс может быть визуально понятным, но непригодным для человека, который пользуется клавиатурой, screen
reader или увеличенным масштабом страницы.

Например, в форме регистрации недостаточно красиво подсветить ошибку: нужна связанная с полем подпись, текст ошибки и
понятный способ перейти к исправлению. Иначе часть пользователей не сможет завершить сценарий, хотя его UI выглядит
законченным.

Доступность не ограничивается постоянной инвалидностью: интерфейс используют и со сломанной мышью, на ярком солнце или
при временном ограничении подвижности. При этом одного checklist недостаточно — сложные сценарии проверяют вручную с
реальными способами ввода.

На интервью важно показать связь **accessibility → успешность сценария → UX**, а не описывать доступность как работу
исключительно с ARIA.





#### Вопрос: Что такое keyboard navigation?

**Короткий ответ**

Keyboard navigation позволяет пользоваться интерфейсом с клавиатуры без мыши. Это важно для доступности, power users и
ситуаций, где мышь неудобна.

**Полный ответ**

Браузер управляет последовательностью фокуса для нативных интерактивных элементов. Обычно `Tab` и `Shift+Tab` перемещают
фокус между контролами, `Enter` активирует ссылку или кнопку, `Space` активирует кнопку, а `Escape` закрывает
поддерживающие это взаимодействие всплывающие элементы.

Для составных виджетов, например tabs, listbox или menu, могут действовать другие правила: `Tab` вводит фокус в
компонент, стрелки перемещают его внутри. Конкретный keyboard contract зависит от паттерна WAI-ARIA, а не придумывается
отдельно для каждого проекта.

Практическая проверка: пройти регистрацию от первого поля до подтверждения, не используя мышь; проверить порядок,
видимость фокуса, открытие и закрытие диалогов, достижимость ошибок. `tabindex="0"` включит кастомный элемент в
последовательность, но **не добавит** ему нативную активацию или семантику. Положительные значения `tabindex` обычно
создают непредсказуемый порядок.

На интервью полезно различать **tab sequence**, **keyboard activation** и **keyboard navigation внутри composite
widget**.





#### Вопрос: Что такое focus state?

**Короткий ответ**

Focus state показывает, какой элемент сейчас активен для клавиатуры. Без него пользователь не понимает, где находится в
интерфейсе.

**Полный ответ**

DOM-фокус определяет элемент, который получает события клавиатуры: это можно проверить через `document.activeElement`.
Визуальный focus state показывает пользователю положение этого фокуса, но не должен подменять фактическое управление им.

Обычно браузер применяет `:focus` к сфокусированному элементу, а `:focus-visible` позволяет показывать заметный
индикатор, когда он особенно нужен при клавиатурном взаимодействии. Однако правило не означает, что при каждом клике
мышью индикатор обязательно скрывается: решение принимает браузер с учетом контекста.

Например, после открытия modal dialog фокус нужно перенести на подходящий элемент внутри. После закрытия — вернуть
инициатору, если он еще существует; если нет, выбрать логичное следующее место. Просто нарисовать рамку вокруг поля
недостаточно.

Распространенная ошибка — менять визуальный класс `.focused`, не вызывая реальное перемещение фокуса. На интервью
свяжите **видимость, DOM-фокус и focus management**.





#### Вопрос: Почему нельзя убирать outline без замены?

**Короткий ответ**

Outline часто является единственным видимым индикатором фокуса. Если его убрать, нужно дать равноценный и заметный focus
style.

**Полный ответ**

`outline` — стандартный способ показать keyboard focus без изменения геометрии элемента. Глобальное правило
`*:focus { outline: none }` часто делает переходы по `Tab` невидимыми, даже если мышью интерфейс работает нормально.

Если дизайн требует собственного индикатора, его можно задать через `:focus-visible`: например, контрастный
`outline: 2px solid currentColor` с `outline-offset: 2px`. Но конкретные цвет и толщина должны подходить реальному фону,
включая dark mode и разные состояния кнопки.

Проверяйте индикатор на кнопках, ссылках, input, элементах внутри dialog и при системном режиме `forced-colors`. Один
лишь `box-shadow` может исчезнуть в high-contrast mode, поэтому системный outline часто надежнее.

На интервью объясните отличие **визуальной кастомизации focus style** от **отключения focus indication**: первое
возможно, второе лишает пользователя ориентира.





#### Вопрос: Что такое semantic HTML?

**Короткий ответ**

Semantic HTML использует элементы по смыслу: button для действия, a для ссылки, label для поля, heading для структуры.
Это помогает браузеру, assistive technologies и разработчикам.

**Полный ответ**

Semantic HTML передает браузеру **назначение и структуру**, а не только внешний вид. Нативный `<button>` имеет роль
кнопки, участвует в tab order и поддерживает клавиатурную активацию; `<a href="...">` предоставляет семантику навигации
и привычные действия со ссылкой.

Например, clickable `<div>` с обработчиком `click` не становится доступной кнопкой автоматически: потребуется роль,
фокус, обработка клавиш, disabled behavior и тестирование. Обычный `<button type="button">` решает большинство этих
задач без дополнительной логики.

Семантика важна и за пределами controls: заголовки `h1–h6` и landmarks помогают screen reader переходить по странице, а
`<label>` дает полю понятное имя. При этом выбор `h2` вместо `h3` нельзя основывать исключительно на размере шрифта —
внешний вид задается CSS.

На интервью приводите **конкретный нативный элемент и его встроенное поведение**, а не только перечисление тегов.





#### Вопрос: Как label связан с доступностью формы?

**Короткий ответ**

Label связывает текстовое описание с полем ввода. Благодаря этому поле можно понять, сфокусировать кликом по подписи и
корректно озвучить screen reader.

**Полный ответ**

Нативный `<label for="email">` связан с `<input id="email">` через совпадающий идентификатор. Браузер использует подпись
как часть accessible name поля, а нажатие на подпись переводит фокус на соответствующий control. Поле также можно
поместить внутрь `<label>` без `for`, если разметка позволяет.

Placeholder не заменяет label: он исчезает при вводе, нередко имеет низкий контраст и не объясняет поле после
заполнения. Для дополнительной инструкции или текста ошибки подойдет `aria-describedby`, который связывает поле с
элементом пояснения.

В динамических формах важно обеспечивать уникальность `id`: если два input используют один `id`, связь подписи может
сломаться. Для группы radio нужны `<fieldset>` и `<legend>` либо эквивалентная доступная группировка.

На интервью различайте **accessible name**, **описание** и **текст ошибки**: у них разные назначения, и одно не заменяет
другое.





#### Вопрос: Что такое alt text?

**Короткий ответ**

Alt text описывает смысл изображения для пользователей, которые его не видят. Он должен передавать функцию или
информацию изображения, а не просто перечислять детали.

**Полный ответ**

Атрибут `alt` определяет текстовую альтернативу содержимому `<img>`. Хорошая альтернатива передает **смысл изображения в
текущем контексте**, а не механически описывает каждый цвет и объект.

Например, если изображение — единственное содержимое ссылки на профиль, `alt="Профиль Анны"` дает ссылке понятное имя.
Если рядом уже есть видимый текст «Профиль Анны», повторяющий его `alt` может создать избыточное озвучивание.

Для информационной схемы короткого `alt` может не хватить: основное объяснение нужно дать рядом текстом или предоставить
доступное подробное описание. Для графика важно передать ключевые данные и вывод, а не только «график продаж».

Не начинайте без необходимости с «изображение» или «картинка»: screen reader обычно уже сообщает тип элемента. На
интервью важно объяснить, как **функция картинки и окружающий текст** определяют `alt`.





#### Вопрос: Когда alt text должен быть пустым?

**Короткий ответ**

Когда изображение декоративное и не несет смысла. Пустой alt позволяет screen reader пропустить его и не создавать шум.

**Полный ответ**

`alt=""` используют, если изображение не добавляет информации или уже полностью дублируется соседним текстом. Например,
декоративный орнамент рядом с заголовком или иконка внутри кнопки с видимым текстом «Сохранить» обычно не нуждаются в
повторном озвучивании.

Пустой `alt` — не то же самое, что отсутствие атрибута: при отсутствующем `alt` некоторые технологии могут попытаться
озвучить имя файла или URL. Для декоративного `<img>` лучше задать явный `alt=""`.

Есть важный edge case: иконка без видимой текстовой подписи внутри кнопки **не должна делать кнопку безымянной**.
Доступное имя задают, например, через `aria-label` на кнопке или через содержательную альтернативу изображения.

На интервью различайте **decorative**, **informative** и **functional** images. Если изображение сообщает критичную
информацию, скрывать ее пустым `alt` нельзя.





#### Вопрос: Как accessibility улучшает UX для всех пользователей?

**Короткий ответ**

Хорошие подписи, контраст, keyboard navigation, понятные ошибки и предсказуемый фокус помогают не только людям с
инвалидностью. Они улучшают продукт в плохом освещении, на мобильных устройствах и при спешке.

**Полный ответ**

Доступные паттерны уменьшают число ситуаций, в которых человек не может понять интерфейс или завершить действие. Крупная
кликабельная область, отчетливая подпись и текстовый feedback полезны при моторных ограничениях, на маленьком экране и в
спешке.

Например, пользователь может временно работать без мыши; корректный tab order позволит продолжить задачу. Субтитры
помогают при нарушении слуха и при просмотре видео без звука. Понятная текстовая ошибка полезнее красной рамки
независимо от способа ввода.

Однако нельзя полагаться только на аргумент «это полезно всем»: некоторые потребности требуют специализированных
решений, например корректной модели screen reader для сложной таблицы. Их проверяют отдельно, а не выводят автоматически
из хорошей визуальной эргономики.

На интервью приведите **конкретную accessibility-механику**, ее результат для основного сценария и отдельную проверку
потребностей пользователей assistive technologies.





#### Вопрос: Почему порядок фокуса важен?

**Короткий ответ**

Порядок фокуса должен соответствовать визуальному и смысловому порядку экрана. Иначе пользователь клавиатуры теряет
контекст и может пропустить важные действия.

**Полный ответ**

По умолчанию браузер следует DOM-порядку фокусируемых элементов. Если CSS визуально переставляет карточки через `order`
или Grid, последовательность `Tab` может перестать совпадать с тем, что пользователь видит на экране.

Например, визуально кнопка «Оплатить» расположена сразу после суммы, но по DOM находится в самом конце страницы.
Пользователь клавиатуры пройдет десятки элементов, прежде чем достигнет действия, которое находится у него перед
глазами.

Для обычного контента лучший подход — **логичный DOM-порядок**, совпадающий с чтением и визуальной структурой.
Положительный `tabindex` не исправляет архитектуру: он создает отдельные правила навигации и особенно плохо
масштабируется в динамических списках.

При открытии modal или удалении строки важен не только порядок, но и осмысленное восстановление фокуса. На интервью
полезно проверить tab order до, во время и после изменения интерфейса.





#### Вопрос: Как проектировать доступный modal dialog?

**Короткий ответ**

Фокус должен переходить внутрь dialog, оставаться внутри до закрытия и возвращаться на элемент, который его открыл.
Нужны понятный заголовок, закрытие с клавиатуры и недоступность фонового контента для взаимодействия.

**Полный ответ**

Для модального сценария предпочтителен нативный `<dialog>` с `showModal()` или проверенный компонент, реализующий
WAI-ARIA dialog pattern. Модальность означает, что фоновый интерфейс недоступен для взаимодействия, а фокус остается в
допустимой области dialog.

После открытия фокус перемещают внутрь на подходящий элемент; заголовок связывают с dialog через доступное имя, например
`aria-labelledby`. `Escape` обычно закрывает обычный modal, но для сценариев с риском потери данных могут понадобиться
отдельное подтверждение или явно описанная политика закрытия.

После закрытия фокус возвращают на элемент-инициатор, если он сохранился. Если диалог удалил этот элемент, выбирают
логичную альтернативу, например соседний элемент списка. Не стоит вручную строить trap вокруг случайного `div` без учета
смены содержимого и вложенных popup.

На интервью раскройте **открытие, keyboard flow, блокировку background, закрытие и восстановление фокуса**.





#### Вопрос: Как проектировать доступное уведомление об ошибке?

**Короткий ответ**

Ошибка должна быть видимой, текстовой и связанной с полем или областью, где она возникла. Для динамических ошибок важно,
чтобы assistive technologies могли узнать об изменении.

**Полный ответ**

Сообщение об ошибке должно объяснять **что произошло и как исправить проблему**, а не только менять цвет поля. Для поля
можно показать видимый текст, установить `aria-invalid="true"` и связать пояснение через `aria-describedby` или
`aria-errormessage` при подходящей поддержке.

Если ошибки появляются после submit, полезно вывести summary в начале формы и перевести фокус на него или первое
проблемное поле. Выбор зависит от длины формы: пользователь должен быстро найти действие и не потерять контекст.

Для динамических сообщений помогают live regions: `role="alert"` подходит для важных ошибок, `role="status"` — для менее
срочного feedback. Не следует одновременно перемещать фокус и дублировать тот же текст в нескольких live regions: screen
reader может озвучить его несколько раз.

На интервью приведите flow **submit → ошибка backend → связанное сообщение → исправление → повторная отправка**, включая
keyboard-only использование.





#### Вопрос: Что такое ARIA и когда она нужна?

**Короткий ответ**

ARIA добавляет семантику там, где native HTML не хватает. Она нужна для сложных custom components, но не должна заменять
обычные HTML-элементы без причины.

**Полный ответ**

WAI-ARIA описывает роли, состояния и связи для accessibility tree: например, `aria-expanded` сообщает состояние
раскрытия, `aria-controls` указывает связанный элемент, а `aria-labelledby` задает доступное имя через другой текстовый
узел.

ARIA не реализует поведение компонента. `role="button"` на `div` не добавляет обработку `Enter`/`Space`, фокус или
disabled semantics. Поэтому нативные HTML-элементы обычно надежнее, а ARIA нужна для случаев, когда семантику нельзя
адекватно выразить обычным HTML.

Пример: кастомный combobox требует не только `role="combobox"`, но и управления фокусом, клавишами, состоянием popup,
active option и озвучиванием выбранного значения. Слепое добавление атрибутов может сделать его менее доступным.

На интервью различайте три слоя: **semantics (HTML/ARIA), behavior (JavaScript) и feedback (визуальный/озвучиваемый)**.





#### Вопрос: Почему сначала лучше использовать semantic HTML, а не ARIA?

**Короткий ответ**

Native элементы уже имеют встроенное поведение, роли, keyboard support и совместимость. ARIA легко применить неправильно
и получить интерфейс, который выглядит доступным только в коде.

**Полный ответ**

Нативные элементы уже участвуют в платформенных правилах: кнопка доступна с клавиатуры, ссылка имеет поведение
навигации, input поддерживает ввод и базовые формы взаимодействия. При использовании кастомных элементов все эти
контракты приходится поддерживать самостоятельно.

Например, `<div role="checkbox" aria-checked="true">` сообщает роль и состояние, но без клавиатурной логики, управления
фокусом и обработки переключения такой control не эквивалентен `<input type="checkbox">`.

ARIA полезна, когда нативного элемента недостаточно: например, для отдельных состояний виджета или доступного имени
icon-only кнопки. Но **no ARIA is better than bad ARIA**: неверная роль может ухудшить понимание интерфейса screen
reader.

На интервью предложите последовательность: найти нативный элемент → проверить его возможности → добавить минимально
нужную ARIA → протестировать реальное взаимодействие.





#### Вопрос: Как цветовой контраст влияет на UX?

**Короткий ответ**

Низкий контраст ухудшает чтение, особенно на мобильных устройствах, плохих экранах и при ярком свете. Контраст важен для
текста, иконок, focus state и ошибок.

**Полный ответ**

Контраст определяет различимость текста и важных визуальных границ. По WCAG 2.2 для обычного текста обычно требуется
минимум **4.5:1**, для крупного текста — **3:1**; для значимых графических элементов и границ controls часто применяется
требование **3:1** при соответствующих критериях.

Например, светло-серый placeholder на белом фоне может быть нечитабельным, а тонкая граница input — неразличимой. При
этом для placeholder особенно важно не делать его единственным носителем инструкции: даже идеальный контраст не заменит
label.

Контраст нужно проверять во всех состояниях: default, hover, focus, validation error, dark theme и disabled. Для
некоторых неактивных компонентов требования WCAG отличаются, но это не повод скрывать пользователю причину недоступности
действия.

На интервью объясните, **какие элементы измеряют**, почему одного брендового цвета недостаточно и как проверяют токены
дизайн-системы на реальных фонах.





#### Вопрос: Почему нельзя передавать смысл только цветом?

**Короткий ответ**

Не все пользователи различают цвета одинаково. Ошибку, успех или выбранное состояние нужно дополнительно передавать
текстом, иконкой, формой или расположением.

**Полный ответ**

Цвет может быть незаметен при дальтонизме, низком качестве дисплея, ярком освещении или при выключенных пользовательских
стилях. Кроме того, screen reader не сообщает различие между красным и зеленым состоянием автоматически.

Например, поле с ошибкой нельзя обозначать только красной рамкой: добавьте текст «Введите корректный email» и свяжите
его с input. В графике различайте серии не только цветом, но и подписями, маркерами или узорами; у выбранного tab должен
быть явный state.

Дополнительный сигнал не обязательно означает иконку рядом с каждым словом. Важнее, чтобы значение состояния было
доступно **в тексте и семантике**; иначе просто добавленная иконка без подписи не решит проблему.

На интервью сравните status badge, форму и график — во всех трех сценариях нужно сохранить смысл при потере цветового
различия.





#### Вопрос: Как тестировать accessibility на базовом уровне?

**Короткий ответ**

Нужно пройти сценарий с клавиатуры, проверить focus states, labels, contrast, heading structure и сообщения об ошибках.
Автоматические проверки полезны, но не заменяют ручной проход.

**Полный ответ**

Проверку удобно разделить на автоматическую и ручную. Axe, Lighthouse или accessibility lint находят часть проблем:
missing names, некорректные атрибуты, отдельные нарушения contrast и структуры. Они не докажут, что пользователь
способен завершить весь сценарий.

Ручной smoke test начинается с клавиатуры: от загрузки страницы пройти `Tab`/`Shift+Tab`, проверить
`Enter`/`Space`/`Escape`, видимый фокус, dialog, формы и сообщения об ошибках. Затем проверить масштабирование до 200%,
увеличение текста, responsive reflow и, по возможности, основной flow со screen reader.

Например, тест может подтвердить наличие `aria-label` на кнопке, но не заметить, что после удаления строки фокус
исчезает или Escape неожиданно закрывает весь экран.

На интервью покажите **матрицу: automated checks + keyboard + screen reader + critical business flow** и объясните
ограничения каждого метода.





#### Вопрос: Какие accessibility-проблемы чаще всего создает frontend?

**Короткий ответ**

Частые проблемы: div вместо button, потеря фокуса, недоступные custom select, слабый контраст, ошибки без текста и modal
без focus management. Большинство из них дешевле исправлять во время разработки.

**Полный ответ**

Типичная причина — замена встроенных browser semantics визуальными имитациями. `div` вместо button, обработчик только
`click`, icon-only control без accessible name и модальный popup без focus management выглядят исправно при тестировании
мышью, но ломают другие способы ввода.

Вторая группа ошибок связана с динамическими состояниями: loading без announcement, форма с ошибкой без связанного
пояснения, обновленная таблица с потерянным фокусом и dropdown, который нельзя закрыть клавиатурой.

Например, при рефакторинге кнопки в «универсальную карточку» можно случайно потерять клавиатурную активацию. Лучший
способ избежать этого — заранее определить семантический контракт компонента и проверять его в unit/component/E2E
тестах.

На интервью важно не только перечислить баги, но и назвать **первопричину, сценарий воспроизведения и защиту от
регрессии**.





#### Вопрос: Как встроить accessibility в Definition of Done?

**Короткий ответ**

Нужно включить keyboard flow, focus state, labels, contrast, error handling и базовые проверки в критерии готовности.
Так accessibility становится обычной частью разработки, а не отдельной фазой в конце.

**Полный ответ**

Definition of Done должен содержать проверяемые требования, привязанные к типу задачи. Для новой формы это labels,
help/error descriptions и keyboard submit; для dialog — управление фокусом и закрытие; для таблицы — корректные
заголовки, состояние сортировки и доступные действия.

Базовые шаги можно автоматизировать: lint, axe в component/E2E smoke tests и проверку семантики при review. Ручной
keyboard pass для критического сценария остается обязательным, потому что автоматические инструменты не оценивают
понятность всего flow.

Не стоит превращать DoD в гигантский универсальный checklist: набор применимых критериев зависит от компонента и
изменения. При этом известные дефекты нужно фиксировать с владельцем и приоритетом, а не считать выполненными из-за
отсутствия новых регрессий.

На интервью предложите **небольшой обязательный набор, конкретные acceptance criteria и процесс для исключений**.





#### Вопрос: Как design system помогает accessibility?

**Короткий ответ**

Design system может централизовать доступные компоненты, цветовые токены, focus styles, labels и примеры паттернов. Это
снижает вероятность повторять одни и те же ошибки в каждом feature.

**Полный ответ**

Design system позволяет централизованно реализовать сложный доступный contract: семантику controls, focus styles,
keyboard behavior, disabled states, подписи и проверенные сочетания контрастных цветовых токенов.

Например, исправление keyboard navigation в общем select может устранить ошибку в десятках приложений, а не требовать
локального workaround для каждой формы. Документация компонента должна показывать не только красивые состояния, но и
правила его использования: обязательное accessible name, error text и edge cases.

Однако библиотека не гарантирует доступность продукта автоматически. Неправильный label, порядок элементов, вложенность
dialog или неуместный tooltip могут сломать сценарий даже на корректных primitives.

На интервью разделите ответственность: **design system обеспечивает accessible building blocks**, а продуктовая команда
отвечает за composition, content и end-to-end flow.





#### Вопрос: Почему accessibility-долг сложно исправлять в конце проекта?

**Короткий ответ**

Потому что проблемы часто встроены в компоненты, визуальный язык и сценарии. Поздняя правка может затронуть дизайн,
архитектуру и уже привычное поведение продукта.

**Полный ответ**

Доступность часто зависит от исходных архитектурных решений. Если десятки экранов используют `div`-buttons, кастомный
focus trap или компоненты без понятной структуры именования, поздний фикс затронет API компонентов, тесты, дизайн и
пользовательские сценарии.

Например, добавление доступной клавиатурной модели в самописный select может потребовать изменить состояние active
option, управление прокруткой, поведение Escape и контракт form control. Это уже не локальная CSS-правка.

Практичнее исправлять основу в design system, защищать ее contract tests и постепенно мигрировать потребителей. Для
существующего продукта полезно ранжировать долг по критичности сценария, числу затронутых пользователей и стоимости
регрессии.

На интервью объясните, почему **поздняя accessibility-доработка может стать cross-cutting refactor**, и как избежать ее
через раннее проектирование взаимодействий.





#### Вопрос: Как обсуждать accessibility с продуктом, если ее считают низким приоритетом?

**Короткий ответ**

Лучше говорить через риск, охват, качество, скорость поддержки и конкретные сценарии пользователей. Полезно предлагать
минимальный обязательный уровень, который команда может стабильно выполнять.

**Полный ответ**

Аргументируйте конкретными потерями для пользователя и продукта: нельзя завершить оплату с клавиатуры, ошибка формы не
озвучивается, модальный диалог блокирует сценарий. Так задача становится воспроизводимым дефектом, а не абстрактным
пожеланием.

Полезно показать короткую демонстрацию и предложить измеримый минимум: доступный вход, регистрацию, покупку и другие
критичные пути. Далее — добавить приемочные критерии и общий набор компонентов, чтобы каждый следующий экран не создавал
такой же долг.

Приоритизация зависит от аудитории, обязательств и масштаба проблемы, но наличие других задач не делает недоступный
сценарий менее реальным. Не обещайте «однажды починить все» без владельца и плана.

На интервью используйте рамку **сценарий → impact → минимальный fix → предотвращение регрессии** и покажите умение
договариваться с продуктом.





#### Вопрос: Как связаны accessibility, legal risk и качество продукта?

**Короткий ответ**

Недоступный интерфейс может создавать юридические риски в некоторых рынках и отрезать часть аудитории. Даже без
юридического давления accessibility является признаком зрелого продукта.

**Полный ответ**

Требования доступности зависят от страны, сектора, типа продукта и применимых норм. Например, в отдельных юрисдикциях
обязательства могут распространяться на государственные сервисы или определенные категории коммерческих продуктов.
Нельзя утверждать, что любой сайт в мире автоматически подпадает под одну и ту же норму.

WCAG — технический стандарт с уровнями соответствия и критериями успеха; его использование в контракте или
законодательстве нужно проверять отдельно. Соответствие checklist не гарантирует безошибочный пользовательский опыт, а
юридическая оценка требует учета контекста.

Для frontend-команды практический вывод один: закладывать доступность в компоненты и проверять критические сценарии
раньше, чем проблемы станут дорогостоящим техническим и продуктовым долгом.

На интервью разделяйте **стандарты, применимые юридические требования и фактическое качество UX**; не подменяйте одно
другим.



### Microcopy и коммуникация интерфейса



#### Вопрос: Что такое microcopy?

**Короткий ответ**

Microcopy - это короткие тексты интерфейса: кнопки, подсказки, ошибки, empty states, labels и confirmations. Они
направляют пользователя в момент действия.

**Полный ответ**

Microcopy — это текст, который помогает человеку понять текущее состояние интерфейса и выполнить конкретное действие.
Его качество определяется не длиной, а тем, отвечает ли он на вопросы **что произойдет, почему и что делать дальше**.

Например, «Сохранить черновик» задает ожидание результата, «Сохранено в 14:32» подтверждает его, а «Не удалось
сохранить. Повторить» дает способ восстановления. Эти тексты образуют один сценарий, хотя находятся в разных
компонентах.

Хорошее microcopy должно совпадать с реальным поведением: нельзя писать «Готово», если запрос еще выполняется или
операция завершилась только локально. При локализации учитывают длину, формы множественного числа и tone of voice;
жестко зашитый в компонент текст быстро становится техническим долгом.

На интервью полезно показать **связь между текстом, состоянием приложения и следующим действием**, а не ограничиваться
перечислением кнопок и подсказок.





#### Вопрос: Где используется microcopy?

**Короткий ответ**

В формах, уведомлениях, меню, onboarding, CTA, validation messages, placeholders и success states. Почти каждый
интерактивный элемент нуждается в понятном тексте.

**Полный ответ**

Microcopy сопровождает почти весь user flow: от названия поля и placeholder до подтверждения платежа, текста загрузки,
сообщения об ошибке и empty state. Особенно важно оно там, где пользователь принимает решение, ждет результата или
исправляет ввод.

Например, экран импорта файлов требует нескольких разных сообщений: поддерживаемые форматы до выбора, прогресс во время
загрузки, причину отклонения конкретного файла при ошибке и результат после завершения. Один общий toast не заменяет эти
состояния.

У текста есть контекст размещения. Короткая подсказка рядом с полем полезнее отдельной страницы документации для частой
ошибки, но длинную инструкцию не стоит постоянно показывать всем пользователям. Для повторяющихся сообщений можно
использовать общие словари, не теряя контекст конкретного действия.

На интервью пройдите **один законченный сценарий** и объясните, какой текст нужен до действия, во время него и после.





#### Вопрос: Почему текст кнопки важен?

**Короткий ответ**

Текст кнопки задает ожидание результата. “Сохранить изменения” понятнее, чем “OK”, потому что описывает конкретное
действие.

**Полный ответ**

Подпись кнопки формирует ожидание **непосредственного результата клика**. Если написано «Отправить заявку», пользователь
должен понимать, будет ли заявка отправлена сразу или откроется дополнительное подтверждение.

В форме с несколькими действиями «Сохранить черновик» и «Отправить на согласование» различают два разных последствия.
Вариант «Продолжить» подходит для перехода на следующий шаг, но вводит в заблуждение, если запускает необратимую
операцию.

Frontend обязан поддерживать обещание текста: обрабатывать состояние загрузки, предотвращать случайную повторную
отправку и показывать результат. Если надпись временно меняется на «Сохраняем…», ширина кнопки не должна неожиданно
сдвигать соседние элементы. Иконка без текста требует доступного имени.

На интервью свяжите **название действия, фактическое поведение и feedback**, а не обсуждайте текст отдельно от
реализации.





#### Вопрос: Чем “OK” хуже конкретного действия?

**Короткий ответ**

“OK” часто не объясняет, что произойдет после нажатия. Конкретный текст снижает риск ошибки и повышает уверенность.

**Полный ответ**

«OK» не объясняет, что именно подтверждается. В диалоге с несколькими возможными последствиями это увеличивает риск
ошибочного выбора, особенно когда пользователь возвращается к экрану после отвлечения.

Для подтверждения удаления понятнее «Удалить отчет» и «Отмена», чем «OK» и «Cancel». Если действие необратимо или
затрагивает других людей, рядом нужно пояснить последствия: какие данные исчезнут и можно ли восстановить их позже.

Однако «OK» не всегда ошибка. В простом информационном уведомлении без альтернативных действий «Понятно» может быть
достаточно, поскольку пользователь ничего не меняет. Контекст важнее универсального правила «никогда не писать OK».

На интервью предложите **критерий выбора подписи**: пользователь должен понимать исход действия по тексту кнопки и
ближайшему контексту, не угадывая реализацию.





#### Вопрос: Почему сообщение об ошибке должно быть понятным?

**Короткий ответ**

Пользователь должен понять проблему без знания backend, HTTP-кодов или внутренних терминов. Хорошая ошибка помогает
продолжить сценарий.

**Полный ответ**

Хорошее сообщение об ошибке обычно состоит из трех частей: **что не получилось, что это значит для данных и какой
следующий шаг доступен**. Внутренний код или stack trace редко отвечает на эти вопросы.

Например, после неудачного сохранения вместо «HTTP 503» полезнее написать «Не удалось сохранить изменения. Они остались
в форме. Повторите попытку». Последнее утверждение допустимо только тогда, когда frontend действительно сохранил
введенные данные.

Ошибки отличаются по контексту: поле с неверным форматом требует локальной подсказки, временная ошибка сети —
возможности повторить действие, а отказ в доступе — объяснения прав без раскрытия защищенных деталей. Не нужно обещать
retry, когда повторный запрос небезопасен или действие уже могло выполниться на сервере.

На интервью покажите **ошибку и recovery flow**, включая состояние данных и риск повторной операции.





#### Вопрос: Как хороший текст помогает пользователю принять решение?

**Короткий ответ**

Он объясняет последствия, ограничения и следующий шаг. Хороший текст уменьшает неопределенность и снижает число
ошибочных действий.

**Полный ответ**

Текст снижает неопределенность, когда объясняет существенные условия **до** действия. Пользователь должен понимать
стоимость, область изменений, доступность отмены и ожидаемый результат, если они влияют на выбор.

Например, при предоставлении доступа фраза «Пригласить участника» неполна, если приглашенный получит права
администратора. Уточнение «Участник сможет просматривать и изменять все проекты» меняет качество решения сильнее, чем
декоративный tooltip.

Важны timing и hierarchy: критичную информацию нельзя прятать в ссылку мелким шрифтом после основного CTA. Но чрезмерное
количество предупреждений тоже вредно — пользователь привыкает их игнорировать. Выделяйте только существенные
последствия, остальное раскрывайте по запросу.

На интервью опишите **решение с риском и какую информацию нужно показать перед подтверждением**.





#### Вопрос: Почему CTA должен описывать действие?

**Короткий ответ**

CTA должен совпадать с намерением пользователя и результатом операции. “Создать проект” лучше, чем “Продолжить”, если
после клика создается проект.

**Полный ответ**

CTA (call to action) должен соответствовать намерению пользователя и ближайшему следующему шагу. Если кнопка запускает
оплату, «Оплатить 990 ₽» понятнее расплывчатого «Продолжить», когда цена уже известна и подтверждается этим нажатием.

Но точная подпись зависит от flow. Если после клика лишь открывается платежный провайдер, «Перейти к оплате» честнее,
чем «Оплатить». При многошаговой регистрации кнопка «Продолжить» допустима, если она действительно переходит к
следующему экрану без необратимых последствий.

CTA нельзя рассматривать изолированно от заголовка, условий и вторичных действий. На мобильном экране текст может
переноситься; решение — адаптировать layout, а не терять важную часть смысла. Для локализации не следует собирать
надписи из отдельных склоняемых фрагментов.

На интервью сравните **фактическое действие и обещание CTA**, затем проверьте, что они совпадают во всех состояниях.





#### Вопрос: Как писать текст для destructive action?

**Короткий ответ**

Нужно назвать действие и объект: “Удалить отчет” вместо “Подтвердить”. Если последствия серьезные, текст должен прямо
сказать, что будет потеряно.

**Полный ответ**

Для разрушительного действия назовите объект, масштаб и возможность восстановления. Диалог «Удалить рабочую область?» с
кнопкой «Удалить рабочую область» понятнее универсального «Вы уверены?», особенно когда рядом существуют действия
архивации и отключения.

Если удаление необратимо, об этом нужно сказать явно и до подтверждения. Если доступно восстановление, не называйте его
необратимым. Для массовых операций уточните количество элементов: например, «Удалить 12 выбранных файлов», но убедитесь,
что число соответствует фактически выбранным объектам.

Не каждое действие требует отдельного confirm dialog. Если действие обратимо и безопасно, undo может уменьшить трение.
Для действительно критичных операций возможны дополнительное подтверждение или ввод имени объекта, но такие шаги должны
соответствовать уровню риска.

На интервью сравните **confirm, undo и дополнительную проверку** и объясните, когда каждый подход оправдан.





#### Вопрос: Как объяснить пользователю сложное ограничение?

**Короткий ответ**

Нужно писать через практическое последствие и вариант решения. Вместо “limit exceeded” лучше: “Можно добавить до 5
участников на текущем тарифе”.

**Полный ответ**

Ограничение лучше объяснять через **наблюдаемую причину, влияние на текущую задачу и доступный путь решения**, а не
через внутренний термин системы.

Например, вместо «QuotaExceededError» можно написать «На текущем тарифе доступно до 5 участников. Удалите одного
участника или измените тариф». Если повышенный тариф недоступен пользователю, не стоит показывать неработающее обещание
обновления.

Предупреждать желательно до заполнения длинной формы, а не только после submit. Для числового лимита интерфейс может
показывать счетчик, но проверка на сервере все равно обязательна: квота могла измениться из-за параллельных действий. Не
нужно объяснять конфиденциальные ограничения, если они раскрывают внутренние правила безопасности.

На интервью покажите **предупреждение до действия, серверную проверку и понятный feedback при гонке состояний**.





#### Вопрос: Почему технические ошибки нельзя показывать как есть?

**Короткий ответ**

Они непонятны пользователю и могут раскрывать внутренние детали системы. Frontend должен перевести ошибку в безопасное и
полезное сообщение.

**Полный ответ**

Технические сообщения часто рассчитаны на разработчика, а не пользователя: содержат названия сервисов, stack traces,
SQL, внутренние идентификаторы или детали авторизации. Они не помогают восстановить сценарий и иногда раскрывают
информацию, которую нельзя показывать клиенту.

Frontend должен работать с **согласованным контрактом ошибок**: машинный код, допустимые поля, безопасное
пользовательское объяснение и идентификатор запроса для поддержки. Код нужен для выбора локализованной строки, но текст
backend нельзя автоматически вставлять в HTML.

При неизвестной ошибке допустим нейтральный fallback с контекстом операции и безопасным вариантом дальнейших действий.
Подробная диагностика остается в защищенных логах, а correlation ID можно показать пользователю для обращения в
поддержку, если это предусмотрено системой.

На интервью разделите **сообщение пользователю, техническую телеметрию и безопасный error contract**.





#### Вопрос: Как переписать backend error в понятное сообщение?

**Короткий ответ**

Нужно сопоставить код ошибки с пользовательским сценарием. Например, EMAILALREADYEXISTS можно показать как “Такой email
уже зарегистрирован. Войдите или используйте другой email”.

**Полный ответ**

Начните с классификации машинных ошибок в контексте операции. Например, `VALIDATION_FAILED` превращается в сообщения у
конкретных полей, `RATE_LIMITED` — в объяснение временного ограничения, а `VERSION_CONFLICT` — в предупреждение о
конфликте сохранения с вариантом перечитать данные.

Не следует автоматически показывать текст backend или опираться только на HTTP status. Один `409 Conflict` может
означать разные бизнес-ситуации, поэтому стабильный код ошибки надежнее парсинга строк. Неизвестные коды должны попадать
в безопасный fallback и диагностику.

Есть важный security edge case: при регистрации ответ «Этот email уже зарегистрирован» может раскрывать наличие учетной
записи. Для публичного восстановления доступа или регистрации формулировки выбирают с учетом угроз account enumeration и
политики продукта.

На интервью опишите **mapping API code → локализованное сообщение → UI state → recovery action**, включая обработку
неизвестного кода.





#### Вопрос: Что лучше: “Something went wrong” или конкретная ошибка?

**Короткий ответ**

Конкретная ошибка лучше, если команда знает причину и следующий шаг. Общий текст допустим только как fallback, но рядом
должны быть retry или способ получить помощь.

**Полный ответ**

Конкретное сообщение полезнее, когда система достоверно знает причину и может подсказать действие. «Файл больше 10 МБ.
Выберите файл меньшего размера» помогает завершить задачу, а «Что-то пошло не так» — нет.

Но недостоверная конкретика хуже нейтрального текста. Если сервер вернул неизвестную ошибку, нельзя утверждать «Нет
интернета» или «Файл поврежден» без подтверждения. Лучше написать «Не удалось загрузить файл» и предложить безопасный
retry или обращение в поддержку.

Контекст и состояние данных важны: после ошибки оплаты нельзя бездумно предлагать «Оплатить еще раз», если результат
первого платежа неизвестен. Сначала требуется проверка статуса операции или безопасная серверная идемпотентность.

На интервью сформулируйте правило: **точность важнее детализации; сообщение должно опираться на известное состояние
системы**.





#### Вопрос: Когда короткий текст хуже подробного?

**Короткий ответ**

Когда действие рискованное, ограничение неочевидное или ошибка требует объяснения. Слишком короткий текст может скрыть
важные последствия.

**Полный ответ**

Краткость работает для привычных и обратимых действий, но опасна там, где нужно понять ограничение, необратимые
последствия или нетривиальный следующий шаг. «Удалить» достаточно для корзины с восстановлением, но не для
окончательного удаления организации со всеми данными.

Полезен **progressive disclosure**: короткое название действия, рядом — ключевое последствие, а подробности по запросу.
Важные условия не должны прятаться только в tooltip, который недоступен при touch или keyboard interaction.

Излишняя длина тоже мешает. Плотный абзац в диалоге трудно прочитать в стрессовой ситуации; его можно разбить на
заголовок, одно предложение с последствием и два понятных действия. При локализации проверяйте переносы и
масштабирование текста, а не задавайте жесткую высоту контейнера.

На интервью объясните **стоимость ошибочного действия** как критерий необходимой подробности.





#### Вопрос: Как microcopy влияет на conversion rate?

**Короткий ответ**

Понятный текст снижает сомнения и ошибки в ключевых шагах. Это может повысить conversion rate без изменения механики
интерфейса.

**Полный ответ**

Понятный текст может уменьшать ошибки, нерешительность и незавершенные действия воронки. Например, пояснение к полю
«Зачем нужен телефон» способно повысить доверие, а явная итоговая стоимость может снизить число отказов на позднем шаге.

Однако **рост conversion rate не гарантирован**: честное раскрытие условий иногда уменьшает мгновенные клики, но снижает
возвраты, жалобы и отмены. Важно оценивать не только CTR кнопки, но и завершение сценария, ошибки, обращения в поддержку
и долгосрочное качество решений.

Изменения лучше проверять через исследование или A/B-тест с заранее выбранной основной метрикой и guardrails. Учитывайте
достаточный размер выборки, сезонность, сегменты и эффект новых пользователей; одна удачная цифра после релиза не
доказывает причинность.

На интервью предложите **гипотезу, вариант текста, primary metric и guardrail**, а не обещайте конверсию от любого
нового CTA.





#### Вопрос: Как microcopy может стать dark pattern?

**Короткий ответ**

Текст может давить, стыдить, скрывать последствия или делать отказ психологически сложным. Тогда он работает против
интересов пользователя.

**Полный ответ**

Microcopy превращается в манипуляцию, когда заставляет выбирать выгодный продукту вариант через стыд, ложную срочность,
сокрытие условий или запутанные формулировки. Например, «Нет, я не хочу экономить» вместо обычного «Нет, спасибо» давит
на человека при отказе.

Другой пример — кнопка «Начать бесплатно», под которой не раскрыто автоматическое платное продление. Даже если формально
ссылка на тариф существует, критичные условия должны быть доступны в момент решения.

Проблема не в убедительном тексте как таковом: ясное объяснение преимуществ допустимо. Граница проходит там, где
искажают факты, затрудняют отказ или обходят информированное согласие пользователя. Это создает риски доверия, поддержки
и соответствия применимым требованиям.

На интервью сравните **честный upsell и манипулятивную подачу одного предложения**.





#### Вопрос: Где граница между подсказкой и манипуляцией?

**Короткий ответ**

Подсказка помогает принять информированное решение. Манипуляция искажает выбор, скрывает цену или давит на эмоции.

**Полный ответ**

Подсказка улучшает информированность и оставляет человеку **реальный выбор**. Например, «Уведомления можно отключить в
настройках» объясняет последствие включения, но не убеждает страхом и не скрывает отказ.

Манипуляция возникает, когда интерфейс намеренно делает один вариант визуально или словесно обманчивым: «Продолжить»
вместо согласия на подписку, негативно окрашенный отказ, заранее отмеченная нежелательная опция или искусственный
countdown.

Проверка практична: одинаково ли понятны оба варианта, раскрыты ли цена и последствия до действия, может ли пользователь
отказаться без лишних препятствий? При этом не любое выделение primary CTA является dark pattern: важны правдивость
сообщения, прозрачность условий и баланс контроля.

На интервью оцените **сценарий выбора глазами пользователя, который не согласен с предлагаемым действием**.





#### Вопрос: Как согласовывать тексты между frontend, product и support?

**Короткий ответ**

Нужно договориться о терминах, tone of voice и источнике правды для сообщений. Support полезен, потому что знает, какие
формулировки пользователи реально понимают.

**Полный ответ**

Тексты стоит рассматривать как **часть продуктового контракта**: product определяет смысл и бизнес-условия, UX
writing/design отвечает за ясность, frontend связывает строку с состоянием приложения, backend задает стабильные коды
ошибок, support помогает обнаруживать непонятные формулировки.

В реальном проекте полезны глоссарий терминов, таблица сообщений и их контекстов, локализационные ключи и review
изменений. Например, текст для `ACCOUNT_LOCKED` нельзя менять без согласования с политикой безопасности и поведением
поддержки.

Ключи локализации должны описывать назначение сообщения, а не текущую английскую строку; нужно поддерживать plurals,
placeholders и контекст. При изменении бизнес-логики важно одновременно обновлять API mapping, документацию и тесты, а
не только перевод.

На интервью предложите **единый процесс владения текстами**, который не заставляет каждую команду копировать строки
вручную.





#### Вопрос: Почему одинаковые действия должны называться одинаково во всем продукте?

**Короткий ответ**

Разные названия для одного действия создают сомнения и ошибки. Единая терминология делает продукт предсказуемым.

**Полный ответ**

Последовательная терминология помогает пользователю переносить привычный опыт между экранами. Если в одном разделе
действие называется «Архивировать», а в другом «Удалить», пользователь может неверно оценить возможность восстановления
данных.

Единый глоссарий и библиотека текстовых паттернов уменьшают расхождения. Но одинаковая надпись оправдана **только при
одинаковой семантике**: «Сохранить» локальные изменения и «Опубликовать» их для всех участников — разные действия,
поэтому насильственная унификация опасна.

Учитывайте локализацию и контекст: прямой перевод термина может быть неестественным, а одну английскую строку иногда
приходится переводить по-разному из-за грамматики. Не склеивайте фразы из мелких строк; задавайте отдельные сообщения
для различающихся сценариев.

На интервью покажите, как **терминология отражает доменную модель и ожидаемые последствия действия**, а не просто
улучшает единообразие интерфейса.
